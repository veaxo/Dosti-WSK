### F02 — Старое показание Ultrasonic может разрешать дальнейшее движение [P1]

Код: [ExampleSubsystem.java:466](/Users/hampthor/Desktop/Dosti_WSK/src/main/java/frc/robot/subsystems/ExampleSubsystem.java:466), [DriveMotor.java:1545](/Users/hampthor/Desktop/Dosti_WSK/src/main/java/frc/robot/commands/auto/DriveMotor.java:1545), [DriveMotor.java:1572](/Users/hampthor/Desktop/Dosti_WSK/src/main/java/frc/robot/commands/auto/DriveMotor.java:1572).

Значение 50 см остаётся конечным даже спустя длительное время после потери датчика, и робот продолжает приближение к порогу 10 см. Существующий `isFrontSonicRangeValid()` нигде не используется; аналогичной проверки заднего датчика нет.

Сценарий воспроизведён на уровне вызывающей команды. Исправление: передавать значение вместе с валидностью/возрастом, прекращать движение при недостоверном измерении, добавить общий тайм-аут действия.

## Неактивные функции и технический долг

Эти пункты отделены от ошибок действующего пути выполнения.

| Пункт | Наблюдение и последствие |
|---|---|
| Сортировка | `sortBall()` нигде не вызывается. Счётчики ожидают `Red ball`, `green ball`, `Yellow ball`, тогда как JSON содержит преимущественно `red_cube` и синие имена. Красные/синие объекты попадут в ветку по умолчанию. После ожидания 0,3 с цель не перепроверяется, а оставшийся в кадре объект может учитываться повторно. |
| Отдельное распознавание | `visionColor()` и `visionAruco()` не подключены к текущему switch. Подтверждение по времени может опираться на один повторно читаемый кадр в пределах общей свежести 2 с; отдельная проверка новых кадров отсутствует. |
| Старые Java-детекторы | `MarkerTemplate` и `ColorObject` не используются. Изменение `ColorObject.OBJECTS` не меняет реальное Python-распознавание. `reloadMarkerTemplates()` фактически только выставляет счётчик в ноль. |
| PNG маркеров | Python не загружает файлы шаблонов, а читает ArUco ID. Локальная проверка PNG с белой рамкой дала: `Marker_1.png` → ID 5 и 4, `Marker_2.png` → 3 и 2, `Marker_3.png` → 11 и 10. Java возвращает `Marker_<ID>`, а не имя PNG. Для классификации целого знака нужна явная схема соответствия. |
| Native-ресурсы старого детектора | `MarkerTemplate.detect()` передаёт временный `new Mat()` в `findContours()` без явного `release()`. Часть временных Mat освобождается только на обычном пути. Это риск при возвращении старого детектора в постоянный цикл, сейчас он не запускается. |
| Триггеры/крестовина OI | `LEFT_TRIGGER` / `RIGHT_TRIGGER` заданы как индексы осей, но методы читают `getRawButton(2/3)`; `getDriveDPadY()` также читает кнопку. Активный Teleop эти методы не вызывает. |
| Углы захвата | `CLAW_OPEN_ANGLE=18`, начальный угол Teleop 15, но нижняя граница оборудования в программе — 20. Реальные команды ограничиваются до 20. Калибровка должна использовать единый источник допустимых углов. |
| Единицы расстояния | Энкодеры возвращают мм, Ultrasonic/Sharp — см, `goForwardDistance(dist)` умножает аргумент на 11,1 без описания единицы и происхождения коэффициента. Это затрудняет проверку маршрута после изменения кинематики. |
| Структура классов | `DriveMotor` содержит 1750 строк, `ExampleSubsystem` — 579; маршрут, vision, манипулятор и датчики тесно связаны. Имена `ExampleSubsystem`, `o_subsystem`, `seve_scan`, `flzek*` затрудняют сопровождение. |
| Владение vision | Автономная команда изменяет `VisionSubsystem`, но объявляет requirement только на `ExampleSubsystem`. Сейчас второй команды vision нет; при её добавлении возможен конфликт управления. |
| Диск и цикл управления | Java читает файл и JSON на каждом periodic; Python делает `fsync` каждого результата. Задержки цикла и нагрузка SD-карты не измерены. Перед заменой протокола следует измерить время обработки и возраст кадров на VMX-pi. |
| Управление процессом | `pkill -9 -f vision_aruco.py` ищет все совпадающие командные строки и не ограничен принадлежащим приложению PID. При штатном завершении Java явного закрытия дочернего процесса нет. |
| Поток и журналы | MJPEG слушает `0.0.0.0` без аутентификации; доступ зависит от сети робота. `vision_aruco.log` и startup log дописываются без ротации. |
| Повторные сохранения калибровки | HTTP-сервер многопоточный; сохранение JSON атомарно, но полный read-modify-write не защищён общим lock. При двух одновременных сохранениях один профиль может потеряться. |
| Документация и воспроизводимость | Нет README, Python requirements, CI или инструкции для стенда. В `.wpilib` указан teamNumber 1234; соответствие реальному роботу не проверено. |
| Git | Утилиты и тесты на момент анализа не отслеживаются Git, хотя изменённый основной код их импортирует. Коммит только отслеживаемых изменений может оставить репозиторий без необходимых классов. |

## Что сделано удачно

- Единственный Python-процесс владеет камерой; переключение режимов не переоткрывает её.
- Обе стороны используют атомарную замену JSON, что уменьшает вероятность частично прочитанных данных.
- Кинематика трёх колёс выделена в чистую функцию; тесты проверяют разделение перемещения и вращения, нормализацию и недопустимые входы.
- Регулятор курса учитывает циклические углы, угловую скорость, насыщение и ограничение интегратора.
- Финальный захват требует свежего кадра, проверяет исходные и сглаженные координаты, учитывает изменение позы камеры и подтверждает положение несколькими кадрами.
- При потере цели в активных этапах приближения привод останавливается; фильтр сбрасывается для повторного поиска.
- Цвет определяется по HSV, а не форме; проверяются шум, обе красные области Hue, неоднородный цвет и разделение компонент.
- Аппаратные ограничения углов находятся в нижнем слое, а диагностика сохраняет причину исключения и этап запуска.
- Телеметрия оборудования ограничена периодом 0,1 с; в рабочих командах нет блокирующих `Timer.delay()` или `Thread.sleep()`.
- Локальная калибровка на ПК привязана к `127.0.0.1`, имеет токен сессии, проверку ROI и идентификатора кадра.
