# Изменения распознавания и visionPickup

6 октября 2026 года. Изменения выполнены поверх существующей рабочей копии. Ultrasonic, Sharp и энкодеры не используются для оценки дистанции в `visionPickup`.

## Цвета

- HSV-диапазоны и имена в `color_ranges.json` сохранены.
- Область должна состоять преимущественно из пикселей выбранного профиля: минимум 80% связной цветной области. Это отсекает подходящее по HSV пятно на объекте с другим основным цветом.
- Сохранена проверка локальной чистоты цвета 75%, добавлена проверка попадания публикуемого HSV в диапазон профиля.
- Цветная область, занимающая более 60% полного кадра, отбрасывается как неподходящая цель захвата.
- Пересекающиеся профили одной цветной области дают один объект в `targetCount`.
- Пересекающиеся HSV-профили получают общий `colorGroup`. При изменении освещения захват сохраняет идентичность цветовой группы; публикуемое имя относится к профилю, действующему в текущем кадре.
- Python подтверждает цель четырьмя разными кадрами за минимум 0,15 с. Кадр без выбранной цели прерывает подтверждение. Допустимый интервал между последовательными кадрами — до 0,35 с: прежние 0,20 с сбрасывали подтверждение даже при стабильных 5 FPS. Длинная пауза требует новых четырёх кадров. После потери выбранной цели новая центральная цель не подменяет её немедленно.
- Класс выбирается по HSV. Совпадающий с шаблоном цвет у постороннего предмета сам по себе не позволяет отличить его от нужного предмета.

## Плавность

- Во время движения первого подъезда положение камеры фиксируется, подъёмник остаётся в поисковой позиции 50°. После подтверждения цели колёса останавливаются и выполняется штатный переход во вторую позу камеры.
- Удалено одновременное непрерывное сопровождение объекта подъёмником и рукой во время движения: оно меняло перспективу и создавало ложное впечатление приближения.
- Коррекция включается при ошибке от 18 px и выключается при ошибке до 10 px. Завершение стадии центрирования внутри зоны 18 px явно останавливает поворот и подтверждает центр по новым кадрам. Ранее сохранявшаяся коррекция могла блокировать переход в `APPROACHING` даже внутри допустимой зоны.
- Разгон и торможение считаются для поступательной и корректирующей составляющих отдельно. При смене направления сначала происходит торможение к нулю. Изменение мощности привязано ко времени; длинный пропуск scheduler не создаёт большого скачка.
- По просьбе пользователя изучен рабочий коммит [562bf2b — vision+hsv py script done for 4 wheel](https://github.com/veaxo/Dosti-WSK/commit/562bf2be2372102fa0d4213f56490daa41edf597). Из него взят диапазон первого подъезда 0,12 → 0,08: команда больше не падает до 0,02 до подтверждения нужной позиции. История, ветки и удалённый репозиторий не изменялись.
- Текущие пользовательские настройки движения сохранены: первый подъезд 0,08 → 0,06, предел поворота 0,04, допуск центрирования 12 px. Отдельная перестановка обзора первой стадии и её таймер удалены после сообщения о повторяющемся FIRST_VIEW_RECOVERY_TIMEOUT. Вторая поза ограничена командой 0,08 с нижним уровнем 0,06, на высоте захвата используется тот же диапазон. Значения являются настройками управления, а не измеренной физической скоростью.
- Боковая ошибка внутри принятой зоны 18 px не снижает поступательную мощность; с 18 до 28 px команда плавно снижается до нуля. Текущий кадр учитывается вместе с фильтром: при исходном X −52 px и сглаженном X −13 px цель не считается центрированной. Ошибка текущего кадра от 28 px немедленно отменяет поступательную команду, сохраняя плавную коррекцию поворота/бокового движения.
- Совместимость старых команд левого/правого моторов обеспечивается трёхколёсной кинематикой `ThreeWheelDrive`: поступательная составляющая делится на `sqrt(3)/2`, поворот использует заднее колесо. Возле захвата боковое движение выполняется тремя колёсами без поворота корпуса. Раскладка моторов и их инверсия сохранены.
- Все откалиброванные конечные углы сервоприводов, их аппаратные ограничения и максимальные шаги сохранены. Шаг в автомате захвата может только уменьшаться относительно прежнего максимума. Промежуточный наклон руки на 5° после первого подъезда больше не выполняется; шаг 5° остаётся только в поисковом сканировании.

## Подъезд и переходы

Java использует горизонтальную ширину `width`, а не большую ось цветового пятна `size`. Фактическое разрешение Python приводится к координатам 320×240. Высокая узкая область больше не может имитировать широкий близкий объект.

Первая стадия готовит второй обзор, а не подтверждает положение внутри клешни. При текущем фиксированном угле сканирования координата Y не измеряет дистанцию, поэтому требования центра Y 155 px и нижней точки 150 px удалены.

Условия начала второй фазы:

| Параметр | Условие |
|---|---|
| Горизонтальная ширина | От 110 px — сохранена пользовательская настройка; соответствие 3–4 см ещё не установлено |
| Нижний край | Не заменяет порог ширины: Bottom 239 px при Width 50 px не разрешает вторую фазу |
| Ошибка X | Не больше 18 px при текущем допуске 12 px, включая сглаженное смещение |
| Кадр | Свежая подтверждённая цель выбранной цветовой группы, валидные координаты 320×240 |
| Подтверждение | Три разных кадра за минимум 0,30 с |

Колёса останавливаются сразу, когда текущий кадр подходит для подготовки второго обзора. Подтверждение проходит уже при остановленных колёсах. Сглаживание ширины больше не задерживает этот переход: если исходная ширина ровно 110 px, фильтр, подходящий к ней снизу, математически мог очень долго оставаться меньше 110 px. Для плавного движения до остановки сглаживание сохраняется.

Удалён ошибочный обход порога ширины по нижнему краю. На скриншоте ширина 50,059326 px, X −14,314859 px и Bottom 239 px ранее вызывали переход без подъезда. Теперь такая цель остаётся в первом подъезде. Предупреждение `FIRST_VIEW_EDGE_NOT_A_DISTANCE` поясняет, что край кадра не измеряет дистанцию. Свежая видимая цель отслеживается по ширине; при боковой ошибке от 28 px поступательная команда отменяется. Потеря цели останавливает колёса и сбрасывает подтверждение. Неизменная ширина при движении приводит к остановке по защите от отсутствия прогресса.

После смены позы кадры сбрасываются и требуются новые изображения. Во второй позе сохраняются минимальные ширина 110 px и центр Y 170 px; на высоте захвата — ширина 120 px и центр Y 175 px. Требование нижней точки 225 px удалено: объект должен быть достаточно большим и центрированным, оставаясь видимым, а нижняя граница служит для остановки. Закрытие клешни требует отдельного подтверждения на высоте захвата.

Если во время поступательного движения ширина не увеличивается хотя бы на 3 px за 2 с накопленного времени движения, устанавливается ошибка `NO_VISUAL_APPROACH_PROGRESS`. Рост проверяется по исходной ширине новых кадров: сглаживание позиции при 5 FPS задерживало заметный рост на несколько кадров и могло ложно активировать остановку. Дополнительный бюджет: 12 с поступательного движения первой стадии и 3 с каждой финальной корректировки. Ожидание и центрирование этот бюджет не расходуют. Ошибка останавливает привод и не разрешает закрытие клешни; повтор возможен новым нажатием Start.

Промежуточное состояние `ADJUSTING_FIRST_VIEW` удалено. Оно изменяло угол руки и ожидало возвращения цели, вместо того чтобы выполнять штатную смену позы. Сообщения `FIRST_VIEW_EDGE_REPOSITIONING`, `FIRST_VIEW_RECOVERY_TIMEOUT` и `FIRST_VIEW_CAMERA_ANGLE_LIMIT` больше не генерируются. Используется обычная последовательность `RAISING_FOR_FINAL_VIEW` → `LOWERING_ARM` → `REACQUIRING_OBJECT`, с остановленными колёсами, открытой клешнёй и прежними целевыми углами.

В текущих пользовательских файлах граница кадра была увеличена до 250 px при изображении высотой 240 px. Она восстановлена на 235 px для финальных проверок. Во второй позе и на высоте захвата обрезание по-прежнему блокирует закрытие клешни и вызывает `SECOND_VIEW_AT_CAMERA_EDGE` / `PICKUP_HEIGHT_AT_CAMERA_EDGE`.

Для калибровки добавлена `Target Width`: исходная ширина текущего кадра, обновляющаяся независимо от состояния захвата и обнуляющаяся при потере цели. `Pickup Target Width` и `Pickup Target Bottom` теперь обновляются по новым кадрам во всех позах активного захвата; раньше они сохраняли последний замер первого подъезда. `Pickup Arm Command Angle` показывает заданный угол руки, а не измерение физического угла датчиком.

Для диагностики добавлены `Pickup Forward Requested`, `Pickup Forward Command`, `Pickup Turn Command`, `Vision Processing FPS`, `Vision Frame Age`, `Color Tracking State`, `Color Candidate Count`. Частота обработки измеряется в Python отдельно от FPS видеопотока Shuffleboard. `CONFIRMING_TARGET` означает наличие цветового кандидата, ещё ожидающего подтверждения; `NO_COLOR_CANDIDATE` означает отсутствие подходящего цветового кандидата.

При ошибке сохраняются `Pickup Failed Stage`, `Pickup Failure X/Y/Bottom/Width/Forward`. Эти значения относятся к моменту остановки; обычные `Target ...` продолжают обновляться. На присланном скриншоте текущие X −52 px / Bottom 239 отличаются от сохранённых сглаженных X −13 px / Bottom 202, поэтому их нельзя считать единым кадром момента ошибки. Предупреждение о потере цели очищается при её возвращении. Потеря цели также сбрасывает подтверждение центра.

## Проверки

- 34 Python-теста проходят: реальные сохранённые HSV-диапазоны, посторонние оттенки, смешанные цветные области, пересечения профилей, смена освещения, последовательность кадров, стабильные 5 FPS с небольшими колебаниями интервала, длинная пауза, запуск процесса с подставной камерой, ArUco.
- 45 Java-тестов проходят: зоны переходов, шум координат, плавность, торможение при развороте коррекции, остановка при отсутствии прогресса, сохранение бюджета после смены обзора, минимальная рабочая команда подъезда, учёт исходного смещения и отмена движения вперёд при потере выравнивания.
- Сборка Java 11 успешна.
- 17 проверок реального `DriveMotor` с аппаратными заглушками проходят: точные координаты скриншота больше не вызывают вторую фазу; неизменная ширина останавливает подъезд; рост ширины при 5 FPS до текущего порога останавливает колёса до догоняющего фильтра. Также проверены разные кадры, потеря цели, защёлка ошибки, запрет захвата по обрезанному второму обзору и отдельное подтверждение на высоте захвата. Сценарий: `/private/tmp/dosti_pickup_phase_replay.py`. Старый `/private/tmp/dosti_pickup_replay.py` относится к удалённой ветке восстановления.
- Откалиброванные конечные углы и максимальные шаги сервоприводов сохранены; команды подъезда адаптированы из рабочего коммита в указанных выше пределах.
- Для запуска на локальном OpenCV добавлена совместимость ArUcoDetector; прежняя ветка API OpenCV 4.4 сохранена и проверена заглушкой. Работа на установленном OpenCV VMX-pi ещё не проверялась.

## Проверка на роботе

Пользователь требует начало второй фазы в 3–4 см от клешни. Сообщённая ширина около 50 px как на 30 см, так и на 3–4 см во время первого подъезда не различает эти положения; снижать порог до 50 px по этим данным нельзя. Нужны исходные `Target Width`, Y, Bottom и одинаковая поза камеры в обоих замерах. Сохранённые 110 px не объявляются откалиброванной дистанцией. Физическая дистанция и положение предмета внутри клешни по тестам не установлены. Для настройки полезно записать `Pickup State`, исходные/сглаженные X, Y, ширину и нижнюю точку, а также видео первой и финальной поз.

Проект не развёрнут на VMX-pi. Для согласованной работы требуется доставить обновлённые Java и Python вместе. Исторический `PROJECT_AUDIT.md` описывает состояние до этих изменений.
